# IPO 정합성 개선 (2026-09-22)

## 추가 검증

- 여섯 기업의 기간별 매각제한 물량을 모두 원문 합계와 대조했다. 와이즈플래닛컴퍼니 7,907,380주, 글로벌테크놀로지 15,286,573주, 덕산넵코어스 11,315,985주를 추가 확보했다.
- 글로벌테크놀로지와 덕산넵코어스는 9월 21일 증권발행실적보고서로 청약경쟁률 및 배정을 갱신했다.
- 브릴스는 9월 22일 조회 시 실적보고서 미발견. `공시 대기`로 표시하고 재조회한다. API 오류는 미공시로 처리하지 않는다.
- 위너스 배정표는 기간 뒤 `확약` 접미사가 없었다. 열 위치와 합계 검산으로 미확약 1,081,518주를 복원했다. 표에 없는 15일 구간은 명시된 0으로 간주하지 않는다.
- 시트 검증은 IPO기관 신청/배정과 기존주주 물량 모두 업로드 후 실제 값을 다시 읽는다.

원문 접수번호는 각 기업 `holder_lockup.rcept_no`와 신청 구간 `rcept_no`에 저장한다.
합계에는 해당 원문 표가 포함하는 상장주선인 의무인수 등도 들어갈 수 있다. 엄밀한 기존주주만의 합계와 구분하여 **매각제한 표 합계**로 해석한다.
상장일·희망가·공모가 등 기존 수기값은 이번 보강에서 변경하지 않았다.
현재 운영 시트에는 위너스 신청 빈칸을 직접 확인했다. 최근 3개 기업은 사용자가 상장일을 넣은 뒤 이미 `구주물량` 검토 대상으로 올라와 있었다.

## 적용한 구조

`DART 원문 → 병합 셀 복원 → 발행증권 분류 → 열 기준 파싱 → 합계 검산 → 정적 JSON → 시트 투영 → 실제 셀 재확인`

- `scripts/ipo_quality.py`: 공통 검증. null/빈칸/음수/잘못된 숫자/추정 0과 명시된 0을 구분한다. 5개 구간 중 하나라도 없으면 완전한 자료로 보지 않는다.
- `scripts/utils/table_grid.py`: 표의 빈 셀, rowspan, colspan, TD/TH/TE를 유지한다.
- `scripts/sources/dart_api.py`: 매각제한물량 열을 직접 지정한다. 유통가능물량을 대신 쓰지 않는다. 병합 수량이 여러 기간에 걸친 모호한 경우와 합계 불일치를 보류한다.
- `scripts/sources/ipo_schedule.py`: 발행증권 제목·표지의 투자계약/채무/수익/파생결합증권 제외. 기업명 블랙리스트나 본문 내 단순 언급으로 제외하지 않는다. 코넥스 신규상장은 제외하되 코스닥/코스피 이전상장은 유지한다.
- `scripts/sheets_sync.py`: 상장일 미정·종목코드 미정도 DART 기업코드로 검토한다. 실제 IPO 여부 검토와 필드 누락 검토를 분리한다. 수요예측 전에는 아직 나오지 않은 신청 결과를 요구하지 않는다.
- 기존주주 탭에는 검산된 상장 전 기업의 기간별 원문 값을 표시한다. 수기 고정/숨김을 보존하고, 임시 수기는 새 공시가 나오면 자동값으로 교체한다.
- IPO기관 신청/배정 셀을 업로드 후 다시 읽는다. 불일치면 검증상태를 경고로 바꾸고 예외를 발생시킨다. `simple_sheet_state.json`은 두 이벤트 탭 업로드 완료 후에만 갱신한다.

## 정기 실행과 운영

### 전체 배치 재실행 회귀 방지

2026-09-22 추가 보완:

- 동일 IPO 조회 기간 안의 투자설명서와 주식/예탁증권 신고서를 접수일·접수번호로 함께 정렬한다. 더 최신인 기재정정/발행조건확정 신고서를 오래된 투자설명서보다 우선한다.
- 첨부정정은 본문 대체 출처에서 제외한다. 채비·에스팀의 첨부정정 원문은 인수계약서만 포함했다. 기재정정 자체를 제외하는 규칙은 아니다.
- 공모 후 보유주식·매각제한·유통가능 열이 있는 전체 분포 표를 일부 임원/대주주 표와 구별한다. 같은 전체 분포 표 중에서는 마지막 표를 선택하며, 최신 표가 틀려도 과거 정상 표로 대체하지 않는다.
- `총계`도 검산하고, 예탁일 기준 기간·날짜·각주만 있는 기간은 상장일 기준으로 임의 변환하지 않는다.
- 실패한 정정 스냅샷에는 이전 검산값을 `last_verified`로 보존하되 현재 상태는 `review`다. 자동 확정값으로 오인하지 않도록 검토 사유와 원문 접수번호, 미확인 수량, 합계 차이를 시트 메모에 남긴다.
- 에스팀의 최신 발행조건확정 신고서는 변경사항만 수록하고 2026-02-04 본문을 참조한다. 원본문과의 대조 없이 이전 표가 그대로 유효하다고 확정하지 않는다.

남은 수동 원문 검증 쟁점: 디티에스 21,730주 예탁일 기준, 인텔리빅스 4,285주 주석 기간,
래블업 65,400주 우리사주 기간, 케이앤에스아이앤씨 61,405주/113,830주 명시 날짜,
나라스페이스 400주 합계 차이, 위너스 실적보고서의 15일 배정 행 미기재.
위너스의 미기재를 자동으로 확정 0으로 바꾸지는 않는다.

기존주주 스냅샷은 투자설명서/지분증권 신고서에서 별도로 선택한다. 최신 공시가
증권발행실적보고서여도 기존주주 표가 없는 보고서로 검산된 값을 덮어쓰지 않는다.
일반 필드 파싱의 조기 종료와 무관하게 기존주주 출처를 확인한다. 정정 투자설명서가
검산에 실패하면 과거 정상 표로 숨기지 않고 검토 상태를 유지한다. 원문 조회 실패는
기존 수량을 보존하되 별도 오류로 표시하고 다음 배치에서 재시도한다.
회귀 테스트는 실제 전체 갱신 함수를 두 번 실행해 새 실적보고서 이후에도 검산값이 유지되는지 검사한다.

기존 정기 워크플로에 아래 검증/보강 단계를 추가한다.

- 전체 배치: 기존 수기 수거 → 전체 수집 → 최대 4개 기업 DART 보강 → 전체 품질 감사 → 시트 업데이트.
- 빠른 배치: 외부 재수집 없이 전체 품질 감사만 실행한다.
- 추가 보강 단계는 8분 제한, 기업당 투자설명서와 실적보고서 각 최대 1건. 최근 상장 90일/상장 전 기업 및 미해결 파싱 항목을 오래된 시도 순서로 순환한다. 실패도 시도일을 기록해 같은 종목이 매번 상한을 소진하지 않는다.
- `data/ipo_quality_report.json`: 기업별 누락 목록과 원천 요청 실패.
- `data/sheet_sync_health.json`: 탭별 실제 시트 반영 검증 결과. 상태 파일은 단순 쓰기 성공이 아니라 재조회 성공 기준이다.
- `data/ipo_schedule.json`: 공시 접수번호, 검산 상태, 기간별 물량, 날짜 후보를 함께 보관한다.

```powershell
python -m unittest scripts.tests.test_ipo_quality
python -m scripts.audit_ipo_quality --write
python -m scripts.audit_ipo_quality --refresh --limit 4 --write
# 특정 과거 기업만 보강
python -m scripts.audit_ipo_quality --refresh --corp-code 01137860 --write
```

DB는 아직 없고 로컬 JSON/CSV와 시트가 동기화되는 구조다. 웹훅만 추가해도 원자적 동기화가 되는 것은 아니다.
향후 DB 전환 시 `run_id`, 원천 해시, 파서 버전, 필드 출처, 수기 잠금, 원천 수정일을 저장하고,
outbox에 시트 반영 작업을 넣은 뒤 읽기 검증까지 성공해야 `synced`로 전환한다.
현재의 clear→write 방식에는 중간 실패·동시 수기 수정 위험이 남아 있다. 다음 단계는 행 ID별 차등 갱신과 낙관적 동시성 검사다.

## KIND와 상장일 수집 판단

사용자가 준 [KIND 예비심사기업](https://kind.krx.co.kr/listinvstg/listinvstgcom.do?method=searchListInvstgCorpMain)은 시장, 신규/이전상장, 심사 결과의 보조 검증에 적합하다.
**심사 승인일은 상장일이 아니며, 여기 없다고 비IPO로 확정하면 안 된다.** 수량 파싱의 대체재도 아니다.

[KIND 공모일정](https://kind.krx.co.kr/listinvstg/pubofrschdl.do?method=searchPubofrScholMain)에는 상장 유형이 있고 증권사 제공 자료라고 명시돼 있다.
이번 확인에서는 메인 화면은 열렸지만 달력 데이터 요청이 **HTTP 200의 시스템 점검 안내 HTML**을 반환했다.
따라서 정상 달력 스키마를 확인하지 못한 상태에서 자동 상장일 갱신을 활성화하지 않았다.
[네이버 IPO 페이지](https://stock.naver.com/market/stock/kr/ipo)도 이번 웹 조회에서 정상 내용을 받지 못했다. 현재 저장소에는 네이버 IPO 상장일 수집기가 연결돼 있지 않았다.

### 권장 우선순위와 장애 처리

1. 수기 고정값 유지. 공식 공시와 다르면 덮어쓰지 않고 충돌 검토.
2. KIND 신규상장 공시의 기업 식별자와 명시된 상장일 확인.
3. KIND 공모일정/주관사 공지로 상장 예정일 교차검증.
4. 네이버·38커뮤니케이션 등은 이용조건과 응답 스키마를 확인한 후 보조 후보로만 사용.
5. 전부 실패하면 마지막 정상값을 유지하고 수집 실패/기준시각을 기록. 조회 실패를 일정 삭제로 해석하지 않는다.

요청은 세션 재사용, 짧은 timeout, 월 단위 캐시를 사용한다. 403/429는 같은 실행에서 해당 출처 중단, Retry-After를 다음 실행에 반영한다.
5xx/일시적 연결 실패만 제한 재시도한다. 프록시 회전·차단 회피는 사용하지 않는다.
상태코드뿐 아니라 Content-Type, 점검 안내 문구, 날짜/기업 필드 유효성을 검사한다.

현재 구현한 `listing_dates.py`는 DART의 명시적 날짜를 **후보**로 저장하고 기존 날짜와 충돌 여부를 남긴다.
동종 기업 비교표의 상장일이 섞일 수 있어 후보만으로 기존 날짜를 변경하지 않는다.
KIND/포털 수집 어댑터와 자동 승격은 실제 정상 응답 검증 후 연결할 남은 작업이다.
